# Code map

**Read this before searching the tree.** It exists so a session can start with
one targeted read instead of a sweep: which file owns what, which document
already answers a question, and where a given name is defined. It is
deliberately short — the depth lives in the documents it points at, and each of
those is worth more than grepping the source it describes.

Paths are relative to `app.gap.Tsum/` unless they are repo-root documents
(`CLAUDE.md` and this file).

`npm run map:check` verifies this file against the tree: a path that moved, a
name family that escaped the file it claims, a source file nobody listed, a
script added without being mentioned. Run it after moving anything.

```
├── .github/workflows/     docs.yml builds website/ and publishes it to GitHub Pages

│                          documents synced in at build time -- website/README.md
└── app.gap.Tsum/          the only package: the Disney Tsum Tsum script
    ├── src/               the script -- concatenated into one bundle, no imports,
    │                      plus tsums.dat, the one file shipped beside it
    ├── tools/             the build and what runs inside it: the host shim, the
    │                      generated docs, the dispatch traces, the checks, releases
    ├── docs/              data the documents are generated from: the observed page
    │                      graph (transitions.json) and the clip library (media.json)
    ├── build/ dist/       build output, git-ignored (also the release zip + .sha256)
    ├── config.json        release identity: game, one entry per channel (name,
    │                      archive, note, and `Status` -- the lowest SkillStatus
    │                      that channel offers), how many versions stay
    │                      installable (version itself: package.json)
    └── build.sh · build.ps1 · debug_deploy.ps1

                           tools/build/, which is the build
```

It runs on **Game Automation Platform** and only that — see
[External trees](#external-trees) and `CLAUDE.md` for what that means. The
tooling that *develops* it is the development toolkit, a separate private
repository beside this one — `DEVELOPMENT.md` § The development toolkit.

## Source map — `src/`

In bundle order (the `files` list in `tsconfig.json`). One clause per file, so
this stays one read: **the long form is each file's own header comment**, which
is where a decision and its reasoning are kept together. For a name rather than
a file, see [§ Where a name lives](#where-a-name-lives).

| File | Owns | Open it when |
|:--|:--|:--|
| `src/shared.d.ts` | Types only, in **all three** compilations (with `src/logEvents.ts`): `SettingKey`, `Settings`, `SkillType`, `BubbleStrategy`, `RecordKey`, `Locale`. | a setting key, a skill id or a language changes |
| `src/globals.d.ts` | Types only: the host API declarations, the shared value shapes, and `interface Tsum` — every prototype method's signature. | the compiler cannot find a host function, or you added a `Tsum` method |
| `src/settings.d.ts` | Types only, **both** page compilations: the page schema (`SettingSpec`, `GroupSpec`, `TabSpec`, `RowKey`), `Preset`, and `PageMessage` — one page's nudge to the other, a topic carrying no values, so the engine stays the one authority on what a setting is set to. | the pages need a browser-side global, or a new page-to-page message |
| `src/strings.d.ts` | Types only, **both** page compilations: `UiText`, plus `UiStrings` mapped over it so a catalogue and the enum are one list. | adding or removing a piece of page text |
| `src/i18n.ts` | The page-side i18n runtime, **both** page compilations. Resolves at render time, never at load, because the language changes under a page that is already up. | a string comes out in the wrong language, or blank |
| `src/uiEn.ts`, `src/uiZhTw.ts` | One language each, keyed by `UiText`. English is the reference and must be complete; a translation falls back key by key. | wrong or missing page text; `npm run i18n:check` for what a language is missing |
| `src/taskController.ts` | `TsumTaskController`, the cooperative scheduler: which jobs are due, in a total order that never falls to iteration, and running one. Five consecutive throws from one job restart the app. | a task never runs, or runs at the wrong cadence |
| `src/runPlan.ts` | **The run's task table**, in both the game and the settings compilations. `buildRun` registers exactly this and the Run order card lists exactly this, so the two cannot drift. | adding a job, changing who goes first, or the Run order card disagreeing with what runs |
| `src/state.ts` | The two script-wide globals: `ts`, `gTaskController`. | almost never |
| `src/utils.ts` | `isSameColor`, `absColor`, `channelDiff`. | colour comparison |
| `src/data.ts` | **Every coordinate and tuning constant, no logic**: the page fingerprints, the navigation plans, and one table per screen a chore walks. Shared tables only — a table one skill reads lives in that skill's file. | the script taps the wrong place, or a screen needs a fingerprint |
| `src/logEvents.ts` | `Log` — the log event vocabulary, one `const enum` per component inside a namespace erased with them. Every `event` name the project writes, declared once. | adding a log event, or looking for where one is defined |
| `src/scriptEvents.ts` | `Emit` — the **emitted** event vocabulary, the same shape and erased the same way. Separate because these are an interface another program reacts to, not a sentence a person reads: renaming one breaks somebody's tooling. | adding an emitted event |
| `src/logs.ts` | The log sentence **registry**, merging one language over English so a partial translation still writes a full record. No text of its own. | adding a language to the game script |
| `src/logsEn.ts`, `src/logsZhTw.ts` | One language each, keyed by the `Log` constants. English is the reference and must be complete; a translation may omit keys. | wrong or missing user-visible log text |
| `src/logging.ts` | The structured logger: one JSON object per line, the run and round correlation ids, the flood guard, and the **ring** of the last records whether or not they were written out, which is what an issue report carries. `LOGGING.md` is the schema. | adding a log line, or changing what every record carries |
| `src/pathfinding.ts` | Board reading and chain planning, no tapping: circle detection, clustering, the connectivity graph, `calculatePaths`, and `boardStillHolds`. Also the **chroma board colour model**, which is what stops red — it sits on hue's wrap — reading as green, and its **texture axes**, which are what tell two greys apart. | chains are short, wrong or slow — the development tools' `chain:bench` says whether the search is the cause; colours that merge or split are the colour model, not the search |
| `src/pages.ts` | `PageRouter` and the `gPages` singleton: score, `observe`, `react`, `detect`, `peek`, `navigate()`, the page sets every narrowed sweep is drawn from, and `perform` — the one place a subscription's `steps` become taps and waits. | how a match is *chosen*, how the queue runs, or which pages a narrowed sweep can see |
| `src/tsum.ts` | The `Tsum` object itself — the world one run is played in, and how every other file reaches the device: the fields, the geometry `init` works out, the capture and touch wrappers, and the two coordinate conversions. The eight files below reopen this prototype. | a tap lands in the wrong place, the geometry is wrong, or you are adding a `Tsum` method with no better home |
| `src/waits.ts` | The four waits: `sleep`, `sleepUntil`, `settleScreen` (wait for the screen to stop moving rather than for a clock) and `settleBoard` (the play square alone, the only part of the board that ever goes still). `mayContinue()` is here too. | a tap lands inside an animation, or a wait costs more than the thing it waits for |
| `src/appLifecycle.ts` | The game app: whether it is in front, which of its two builds this device plays (`gameBuild`: in front, else last seen, else installed via `pm path` — no setting), getting it there, and the two waits either side of a restart — which watch focus and the first fingerprint rather than a clock. | the game is not running, the wrong build is launched, a restart leaves it somewhere odd, or a tsum is named in the wrong language |
| `src/board.ts` | Reading the board and drawing chains on it: `scanBoardQuick` (one capture, with the bubbles read off that same frame so a pop costs taps and no capture), `link`, and what the Bubble Strategy setting comes to — including the hold over it in a fever's last seconds, and `ripeGameBubbles`, which leaves a bubble with no tsums round it for the next scan. | chains are drawn wrong, bubbles are spent wrong, or the board reads wrong |
| `src/play.ts` | One round, start to finish. Two things make a round hard to end and both live here: proving game over through a burst's animation, and the dead-scan block that notices a chain the game refused. The Max Round Duration cap is the third — the clock giving up on a round that never ends. | a round will not start, ends early, runs forever, or the same few tsums are drawn at with nothing clearing |
| `src/mail.ts` | The mailbox chore. The rows are *found* on the frame rather than measured, so a scrolled list that came to rest between rows still reads. | a gift is missed, a skipped medal or ruby is opened, or the flow sticks on the gift screen |
| `src/hearts.ts` | The send-hearts sweep: rows found wherever the pink is rather than at measured positions, and the end of the list defined as the point a drag stops changing anything. Also the sent/received tally that survives a restart. | hearts are missed, sent twice, or the sweep will not reach the end of the list |
| `src/levelCap.ts` | The level-cap sweep: the sort round trip, the rewind, and one raise at a time off a grid re-read after each, because a raise can move its card out of the order the collection is sorted by. Also Auto Unlock MyTsum Level: the padlock read off the post-round level-up panel's first card, and the one raise after the round that shares the sweep's last three hops. `awaitPage` is shared with `src/boxes.ts`. | a raise is missed, the sweep stops early, it walks the collection in the wrong order, or the MyTsum's cap is read wrong off the level-up screen |
| `src/boxes.ts` | The Box Buying chore. Stops on the game's own two signals or its own purchase limit, and waits for the store's *contents* rather than for the screen to stop moving — it fingerprints as itself about 1.5s early, holding still the whole time. | the wrong box is bought, nothing is bought, or the reveals will not clear |
| `src/fever.ts` | Fever time: one look with no memory, how long the fever has left (the bar's fill, off a crop read when asked), plus `gFever` — the debounced state and its start/end broadcast. A mode of the board, not a page, which is why it is not in `src/pages.ts`. | anything that has to know a fever is running, or about to end |
| `src/lorcana.ts` | The Lorcana transformation: the medallion reader, the state kept off it with hysteresis each way, and the ink-stone bubbles. A mode of the board like `src/fever.ts`, and one setting rather than a skill — every Lorcana tsum transforms the same way whatever its own skill does. | the card is not tapped, the transformation is called early or late, or the ink stones pile up |
| `src/skills/` | One file per skill plus the shared core — see [the skills table](#skills--srcskills). | a skill misfires |
| `src/clickAssist.ts` | Click Assist: read the raw Linux touch stream and draw a chain where the user taps. Mutually exclusive with auto-play. | manual-play mode only |
| `src/dialogs.ts` | Android **system** dialogs (root warnings, permissions) — read by panel colour, with a `uiautomator` XML fallback when that is ambiguous — and the `checkStall` progress watchdog. | the script is stuck behind something the game did not draw |
| `src/corpus.ts` | Capture of unrecognised screens on the device, with sidecars, rate-limited per session — the frames the detection suite's corpus is grown from. | the "collect unknown screens" path |
| `src/report.ts` | **The folder a player sends in.** One per issue: the screen, the router's recent frames, a manifest of everything a screenshot cannot carry, and the last few hundred log records — **including the debug ones the log file never gets**. Every part is written under its own guard, because a screen that will not capture is itself a finding. | a report is empty, misses the screens before the moment, or a new failure should write one |
| `src/walkthrough.ts` | The walkthrough recorder. A *mode*: with that setting on it is the only task, and it watches rather than plays — it never calls `detect()`, so no handler fires and nothing taps. Feeds `docs/transitions.json`. | recording the real page graph, or where a button is |
| `src/roundStats.ts` | The per-round CSV, one file per day: template digit reading (the engine has no OCR), the sampling hooks, the read-modify-rewrite the engine's lack of append forces, and the row `id` — minted at the whistle rather than at the write, because it is the **round's** id and every `round.*` event carries it. Also which tsum is selected, read against the library. | a stats column is empty or wrong, the banner names the wrong tsum, or a row never reaches the server |
| `src/tsums.dat` | **Generated, never hand-edited, and not part of the bundle**: the tsum library — one signature, a name per game build and one board colour for each of 797 tsums. Deployed beside the bundle; a missing or stale one empties the CSV's `tsum` column rather than stopping anything, and the two halves are versioned apart in its header. | never — the development tools' lexicon regenerates it |
| `src/forecast.ts` | **What the script is about to do, without doing it** — which subscription will act, which task the scheduler takes next, and the ways off this screen — each answered from what already decides it rather than from a second reading. Read **forward only**. | the `forecast.state` record is wrong, or a handler was added that can decline |
| `src/pageHandlers.ts` | **Every reaction to a page**, one subscription each; reading it top to bottom is reading the dispatch order. Each is a list of `steps` rather than a body, so the budgets are data and `PAGE_DISPATCH.md` states them. | a screen is recognised and nothing happens |
| `src/index.ts` | The entry point and *only* that: `start()` / `stop()` (and `requestStop()`, the flag-raising half a task body may call), the run lifecycle between them, and the globals beyond them that the settings page evaluates by name. Keep it thin — see `DEVELOPMENT.md` § The one thing to understand first for what a fat one cost. | wiring a setting onto `ts`, registering a task, or a stop/restart behaving oddly |
| `src/quickbar.ts` | The engine half of the **Quick Bar** — the strip of live settings the host draws below the game's own lowest button. Three entry points and nothing else. **Waiting for the next round is the default**: a setting the current round was set up under cannot be decided again under a board already dealt. | a Quick Bar control does nothing, or a pause does not pause the round |
| `src/settings.ts` | The settings WebView, compiled separately: the `tabs` schema, template-cloning rendering, debounced persistence, share codes, the Run order card, and the app bar's preset controls. A preset and a settings code carry the same set (`SHARE_SLOTS`) — how a round is played, and nothing else. A row below the channel's floor is not drawn and takes no stored, shared or preset value, but keeps its slot and its default in `start()`. | adding a setting or a task (also edit `src/index.ts`) |
| `src/index.html`, `src/index.css` | The settings page shell: the app bar, the tab bar, and one `<template>` per piece of structure that `src/settings.ts` clones. Pico CSS plus the components it lacks. Both inlined at build time. | settings page layout |
| `src/releaseStatus.ts` | `ReleaseStatus` and the channel floor stamped into it, **both** page compilations: what this build is allowed to offer, asked as `offeredHere`, plus the badge an unfinished thing wears. Read by the skill list and the settings schema alike. | a skill or setting should reach only some channels |
| `src/skillOptions.ts` | The Skill Type dropdown, written once for **both** page compilations: the entries, their three groups, and each one's required `status`. Not in the game bundle. | adding a skill to the dropdown, deciding its group, or which channels should offer it |
| `src/bubbleOptions.ts` | The Bubble Strategy dropdown, written once for **both** page compilations. Each entry carries a `short` as well as a `title`, because the strip's chip is a few characters wide and which words survive that is a translation decision. | adding a bubble strategy, or the strip's chip reading wrong |
| `src/presets.ts` | **Named configurations, and the store both pages read them from.** `presetMatchName` answers *which preset the form currently is* by matching rather than remembering, so nothing has to be invalidated. Held as values rather than as a code, because decoding needs the schema and the strip's compilation has none. | a preset is not found, not saved, or the wrong one is named |
| `src/qrCode.ts` | A QR encoder and nothing else — byte mode, level M, versions 1–6. In the **settings** compilation only. No library, because the page is loaded from `file://` and inlined whole. | the QR will not scan, or the share code outgrows version 6 |
| `src/quickbarPage.ts` | The Quick Bar's page script, a third compilation: **wiring only**. It finds the controls the markup already declared, by their `data-key`, and keeps them in step with the engine. Every change is debounced and written twice, so the strip draws from the tap rather than from the reply. The Report chip is the one control live while the run *goes*: `qbNameHotspot` hands its rect to the host, which keeps that patch touchable. | a Quick Bar control is wired wrong, or Report is dead mid-run; never for layout |
| `src/quickbar.html`, `src/quickbar.css` | **The Quick Bar's whole appearance**, and the file to edit when iterating on it. Every control is written out by hand with a `data-key` and nothing else, so moving or restyling one needs no change to the script. | Quick Bar layout |

## Skills — `src/skills/`

Each file registers itself with `registerSkill({types: [...]})` and is otherwise
a leaf: nothing outside `src/skills/` references its symbols. Adding one means a
new file here, a line in `tsconfig.json` after `skillCore.ts`, a `SkillType`
member in `src/shared.d.ts`, and a dropdown entry in `src/skillOptions.ts` —
under the group its activation belongs to, at its name, with the `status` saying
how finished it is. A new skill is almost always `SkillStatus.Alpha`, which lists
it on Alpha builds only; promoting it later is a one-word edit.

The Note below says only what makes a skill unlike the others — **how one works
is its own file's header comment**, which for the long choreographies runs to a
hundred lines and more.

## Tooling map — `tools/`

Everything here runs on the PC, in Node, against the **built** bundle — never on
the device — and everything here is part of the build or a check the build
runs. The development toolkit beyond that is a separate private repository
that runs against this one's build: `DEVELOPMENT.md` § The development toolkit.

| Directory | What it is | Entry points |
|:--|:--|:--|
| `tools/runtime/` | The Node stand-in for the host: `load.js` evaluates the built bundle in a vm, `host.js` shims the ~15 host primitives under it (faithful to the app's C++), `imageio.js` and `matcher.js` are the image work those need, and `transitions.js` reads and writes `docs/transitions.json`, the observed page graph. Every harness — here and in the development tools — goes through this, so the matcher under test is the production one | required by `tools/minify/`, `tools/pageDocs/`, `tools/dispatchEval/`, `tools/liveSettings/` |
| `tools/pageDocs/` | Renders `PAGE_DISPATCH.md` by asking the compiled router for its real dispatch order | `npm run pages:docs`, `pages:docs:check` |

## Before editing anything

The rules that are silent when broken. `DEVELOPMENT.md` explains each.

1. **No imports, no modules.** Every `src/*.ts` is concatenated into one
   `build/index.js` and shares one global scope. Order in `tsconfig.json`
   matters for load-time work; duplicate names silently overwrite.
2. **Adding a `Tsum` method means adding its signature to `interface Tsum`** in
   `src/globals.d.ts`. The class is reopened from ten files by declaration
   merging.
3. **Three compilations.** The game bundle (`tsconfig.json`, strict, ES2023),
   the settings UI (`tsconfig.settings.json`, ES5, loose) and the Quick Bar page
   (`tsconfig.quickbar.json`, ES5, strict). The bundle shares only
   `src/shared.d.ts` and the `start({...})` string with the other two; the two
   pages also share `src/settings.d.ts`, `src/strings.d.ts`, `src/i18n.ts`, the
   `ui` catalogues and `src/skillOptions.ts`. Only the first
   has a name an editor discovers, so `settings.ts` carries `/// <reference>`
   lines to keep one from checking it against nothing -- `npm run typecheck` runs
   all three.
4. **A setting is named by `SettingKey`, never by a literal**: add the member in
   `src/shared.d.ts` — `interface Settings` is keyed from it — then the row in
   `src/settings.ts` and the read in `src/index.ts`. Misspelling one is now a
   build error; *forgetting* the read in `index.ts` still is not.
5. **String vocabularies are `const enum`s** — `PageName`, `SkillType`,
   `SettingKey`, `RecordKey`, `SkillReadiness`, `KeyCode`. Use the member, not
   the literal.
6. **`PAGE_DISPATCH.md` and `EVENTS.md` are generated.** Change
   `src/pageHandlers.ts` or an `emitEvent` call and rebuild; editing either
   document by hand is lost at the next build.
7. **Some oddities are deliberate.** This package was forked from a Robotmon
   script and its behaviour was held identical to that original for a long time,
   so a value or an ordering that looks arbitrary may be load-bearing and
   uncommented. Prefer a measurement to a tidy-up — `DRIVING_SCREENS.md` § 5 is
   the worked example.
8. **The version lives in `package.json` and nowhere else.** The settings page
   carries a `$VERSION` placeholder, substituted at build time beside
   `$BUILD_DATE`, and so does the game bundle (`ScriptVersion`, `src/data.ts`,
   stamped on the way into `dist/` so the round-stats CSV can say which build
   played a round); `tools/release/config.js` `loadVersion()` is the reader.
9. **Robotmon is gone on purpose** (ES2023, quality-100 captures, no
   `BOOTCLASSPATH`, no guards around optional natives) — `CLAUDE.md`.
10. **The settings page is a WebView in an overlay window**, so it gets no
   native popups (a `<select>` renders, then does nothing at all when tapped)
   and no `location.reload()` (it navigates to the script directory and blanks
   the page). Redraw with `renderPage()` instead — `DEVELOPMENT.md` § The page
   runs in an overlay.
11. **A log line is one JSON record, not a sentence.** `console.log` is the
   logger's own business; everything else goes through `logInfo` and friends,
   and values go in *fields* rather than concatenated into the message. The top
   level is a fixed envelope and everything a call site says lands in `data` —
   so nothing new belongs at the top level unless it would be true of a log line
   in any program. One plain-text line is all it takes to break a JSONL reader on
   the far end, which is why the settings page and the host app match.
   `LOGGING.md`.
12. **Every timestamp is UTC.** `Date.now()` is epoch milliseconds, log records
   are `toISOString()`, and the stats CSV writes `YYYY-MM-DD HH:MM:SS` off the
   `getUTC*` getters -- file names, day buckets and debug-shot stamps included.
   A local-time reading (`getHours`, `toLocaleString`, a bare `new Date(y, m, d)`)
   makes files from two devices unmergeable, which is the whole point of the
   `id` and `datetime` columns. The PC tooling follows the same rule.

  measurements that need an untouched screen, captures included; `guard`,
  `dismiss` and `navigate` may tap; `notify` decides nothing. A handler that
  captures belongs in `record` — which is where the fever reading is, and why.
  Nothing checks this, and `PAGE_DISPATCH.md` will happily document the wrong
  choice.
- **Bubble taps go through the Bubble Strategy setting, or they are an
  override that says so.** Bubbles are worth more popped inside a chain than
  popped alone, so the play loop hoards them: `popGameBubbles` spends only what
  `bubbleTapBudget` allows, and the periodic blind sweep runs under one strategy
  only — and not even then while a skill's claim stands, since a blind sweep
  cannot respect one. Two deliberate exceptions, and both say so in `registerSkill`:
  `sweepsBubbles` + `clearAllBubbles`, for skills that turn tsums *into* bubbles
  and so have no chain to save them for; and `claimsBubbles`, for a skill that
  makes the chain itself, where the strategy's own pop is a link taken out of it
  (`bubbleTapBudget` returns 0 while the claim stands, and what the skill still
  wants spent it asks for per chain through `popBubblesAfterChain`). A new tap on a
  bubble that reads none of these silently undoes the setting.
- **A mode of a screen is not a page, and must not be read as one.** `variant`
  is documentation and tooling *by contract* (`PageDef` in `src/globals.d.ts`) —
  the script only ever learns the page name — so state like "a fever is running"
  is read from its own probe table (`ts.isFeverTime`), never from the matched
  key. Declaring the entry anyway is usually worth it: it gives the corpus
  configuration something to be tested against. Make it the plain entry's probes
  *plus* the new ones, because `betterPageMatch` ranks on probe count first and a
  shorter entry can never win.
  **Usually, not always** — a mode too small to survive the capture path cannot
  have an entry at all, and must not be given a `variant` either, because a
  configuration nothing fingerprints reads as a missing entry for ever.
  Formal Beast's twin gauge is the case: its channel is ~20 logical px thick,
  three pixels on the 360px-wide capture page probes are read from, so it is
  read at native resolution off a crop instead (`Tsum.readFormalBeastGauges`) and
  its three corpus frames are plain `GamePlaying`. The rule for deciding is the
  studio's probe sweep: if nothing usable separates the mode from the page's
  other frames, there is no entry to write.
- **Detection claims are cheap to prove, so prove them.** The detection suite
  runs production detection over its corpus, and against `dist/index.js` over
  what actually ships. Anything beyond page matching — a watcher, a state
  machine, a new `Tsum` method — can be driven the same way: `createRuntime` and
  `createTsum` from `tools/runtime/load.js` give you the real bundle over a real
  frame in a few lines.

Finish with `map:check`, `pages:docs` (or a build), and a `CHANGELOG.md` entry
under the section for the version
in `package.json` — plus a one-line `### Summary` bullet there if a player would
notice the change.

## Keeping this file true

`npm run map:check` (also run, non-fatally, by the build) checks that:

- every path mentioned here exists;
- every `src/` file, `tools/` directory and Markdown document is mentioned here;
- every name family above really is confined to the files it names, and matches
  at least one symbol;
- every `SkillType` in the skills table is registered in the file beside it;
- the command table and `package.json` scripts agree.

A section that talks in another tree's paths marks itself `<!-- map:external -->`
and is left out of the path check until the next heading.

What it cannot check is the prose, and there is one rule it cannot enforce:
**a row here is a clause, not a paragraph.** This file is read before anything is
searched, so its cost is paid by every session; the reasoning behind a row
belongs in the header comment of the file it names, where the code that would be
changed is in front of you. The three inventory tables were 63% of this document
once, restating headers that were already better. When a file's job changes, its
row here is part of that change — as one clause.
